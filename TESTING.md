# Testing

## Rules (they come from real mistakes)

- **Test from the app.** After any change in `kit/`: quit the game and the app, `./build-app.sh`, `rm -rf /Applications/Siliconium.app && ditto dist/Siliconium.app /Applications/Siliconium.app`, `codesign -v`. The app runs its bundled kit (a stale app caused a false "DirectX error" once).
- **One change at a time, measured before and after, same spot, same conditions.**
- **Measure with the game frontmost.** A game started from a background process (a terminal, a script) is never activated by macOS: no display capture, composited, throttled — CoD1 measured 17-55 FPS that way vs 44-55 frontmost. Either the player starts it from the app, or the test brings the game window to the front.
- **Back up the game's config before experiments.** Q3/IW games write changed cvars at once (a `+set` on the command line persists into the next run; a windowed test leaves `r_fullscreen 0`).
- `sample` (CPU profile) slows the game while it runs: take FPS first, sample afterwards.
- Never auto-close a game the player is using; a watchdog may only close a game that is frozen.
- Window-only screenshots (`screencapture -l <windowid>`), never the full screen.
- Launching from a terminal makes macOS ask the terminal for the microphone; that prompt steals focus (~61 FPS cap).

## Tools

- `MVKCACHE_FPS=1` (settings.conf): `[fps] avg / median / 1% low / worst` every 5 s in `logs/<game>-<mode>.log` for D3D9/DXVK games. OpenGL games (CoD1): Wine's `+fps` channel (`WINEDEBUG=-all,+fps`, set by launch.sh when `MVKCACHE_FPS` is on).
- `GAME_ARGS="+devmap <map>"` / `DISPLAY_MODE=0` / `WINEDEBUG=…` in the environment of `launch.sh` reach the game (`launch.sh steam <id>-<part>`).
- Direct3D 11 games (DXMT: BO2, Ghosts, AW, BO3): `MTL_HUD_ENABLED=1` + `MTL_HUD_LOG_ENABLED=1` in settings.conf (quit the app first: it rewrites settings.conf from its memory). Apple's HUD then logs `metal-HUD: <frame>,<mem>,<mem>,<interval ms>,<GPU ms>,…` (one pair per frame) to the unified log; read it after the run with `log show --start "<time>" --predicate 'eventMessage CONTAINS "metal-HUD"'` (the process is the exe's name when the app starts the game, `wine` when a shell does). The HUD is visible on screen while on. Physical display mode changes: `log show --predicate 'process == "WindowServer" AND eventMessage CONTAINS "set digital mode"'`.
- GPU and per-thread CPU: `ioreg -r -d 1 -c IOAccelerator` ("Device Utilization %") + `ps -M`.
- CPU profile: `sample <game pid> 3 -file out.txt`. Pick the process whose `ps -o comm=` ends in the game's exe (not `start.exe`, not `iw6-focus`). Windows-side frames are unnamed; the unix-side libraries (opengl32.so, GLEngine, AppleMetalOpenGLRenderer, winevulkan, libMoltenVK) are named.
- Window state: `CGWindowListCopyWindowInfo` (owner, layer, on-screen, bounds). Layer 2147483630 + shield windows = display captured; `NSWorkspace.frontmostApplication` needs a run loop to be current.
- Win32 window state from the Mac side: a tiny EnumWindows probe (IsWindowVisible / IsIconic / GetWindowPlacement / GetForegroundWindow, filtered by the game's exe) run in the game's prefix with the same `WINEMSYNC=1` as the running wineserver (without it Wine exits 1 silently). WWII's black screen after Cmd+Tab was its window iconic at -32000,-32000; after the restore it was not the foreground window until `SetForegroundWindow`.
- WWII checks: campaign load = Resume on MISSION SELECT → first frame of play with GPU load (Metal HUD log), ~112 s on an M1 Pro for the first mission (~157 s with `WW2_PRELOAD=1`); `players2/user_config.cfg` must read `seta r_preloadShaders "0"` after a start. Minimized window: minimize the game's window (or switch apps while a mission or match loads), make the game the active app again: the log shows "restored the game window in Wine" and the window is back at 0,0 with the picture moving (EnumWindows probe above: `iconic=0`). A window that only moved off screen (-16000) is moved back instead.
- WWII multiplayer checks: after a start, `players2/user_config_mp.cfg` reads `seta com_maxfps "<display Hz>"` and the game's command line has no `com_maxfps`. Online (a private custom match, never a public one), Steam's prefix has `system32\wininet.dll` = `payload/steam/wwii-wininet.dll` and `system32\wininet_wine.dll` = the engine's `lib/wine/x86_64-windows/wininet.dll`, `HKCU\Software\Wine\AppDefaults\s2_mp64_ship.exe\DllOverrides` has `wininet`=`native` (`builtin` with `WW2_NETSTATE=0`), and the match runs at the GPU's pace (frame time median ~15 ms on an M1 Pro, not 27 ms). Build: `x86_64-w64-mingw32-gcc -shared -O2 -s -nostdlib -Wl,--entry,DllMain -o wwii-wininet.dll tools/wininet-netstate.c tools/wininet-netstate.def -lkernel32`; regenerate the `.def` from the engine's `wininet.dll` export table when the engine changes (named exports forwarded to `wininet_wine`, same ordinals; the four `InternetGetConnectedState*` names implemented). Other programs in the prefix keep Wine's built-in wininet (built-in first ignores the file in system32).
- Steam's launch questions: `logs/console_log.txt` in Steam's folder (`ExecuteSteamURL`, `waiting for user response to ShowLaunchOption / ShowGameArgs`).
- Focus/window events: `WINEDEBUG=-all,+event,+macdrv,+win` (APP_ACTIVATED/DEACTIVATED, ShowWindow, SetForegroundWindow).
- Q3 console log: `+set logfile 2` → `main/console.log` (CoD2) / `Main/console.log` (CoD1).
- DXVK shaders: `DXVK_SHADER_DUMP_PATH=Z:<folder>` dumps `.dxso`/`.spv`; check with `spirv-dis` / `spirv-cross --msl --msl-argument-buffers` (Homebrew).
- Methodology for the published games (cold caches etc.): `docs/OPTIMIZATION-NOTES.md`.
- Battle.net section: `kit/battlenet.sh status|library|state bo4` (no window). Battle.net's own logs are in `prefix-battlenet/drive_c/users/crossover/AppData/Local/Battle.net/Logs` (`battle.net-<UTC time>.log`, a new one per start; a sign-in writes `[BNLogin] … Logged into Battle.net successfully.`; `libcef-*.log` for its web view); its standard output (and Chromium's errors) in `logs/battlenet.log`; the game start in `logs/battlenet-<id>.log`. Installed games: `python3 -I kit/tools/battlenet-products.py [--dump] <prefix-battlenet>/drive_c/ProgramData/Battle.net/Agent/product.db`. A crash of one of its processes: `WINEDEBUG=-all,+loaddll,+seh` on `battlenet.sh start` gives the faulting address and every module's load address (Wine's crash dialog is off in that prefix and winedbg's backtrace does not reach the log).

## Building our binaries

- **32-bit DXVK** (`payload/i386-windows/d3d9.dll`, and `payload/steam/cod2-d3d9.dll`): base = CrossOver 26.3 sources `sources/dxvk` + `src/dxvk/dxvk_pipecompiler.{cpp,h}` from Gcenx DXVK-macOS commit `9c00fdf9` ("[dxvk] async"); then `patches/dxvk-d3d9.patch` applies cleanly (`patch -p1`). Build: `CXXFLAGS="-include cstdint" meson setup build32 --cross-file build-win32.txt --buildtype release` (no `b_ndebug`: the payload keeps libstdc++ assertions), `ninja -C build32 src/d3d9/d3d9.dll`, `i686-w64-mingw32-strip`. Verified: same size (3 358 720) and strings as the payload. For the engine copy write `"Wine builtin DLL\0"` at offset 64; a **native** copy must not carry that mark. CoD2's variant: also `patches/dxvk-d3d9-sm1-samplers.patch`.
- **64-bit DXVK** (`payload/dxvk64/d3d9.dll`): Gcenx DXVK-macOS 1.10.3-20230507 + `dxvk-d3d9-x64.patch` + `dxvk-x64-async2.patch`; `meson setup build64 --cross-file build-win64.txt --buildtype release -Db_ndebug=true`, `ninja -C build64 src/d3d9/d3d9.dll`, strip. x64 DXVK knows only async 1 and (with our patch) 2.
- **DXMT x64 PE side** (`payload/dxmt/x86_64-windows/d3d11.dll`, and `payload/steam/aw-d3d11.dll`): github 3Shain/dxmt tag `v0.80` (589adb7) + `git submodule update --init --recursive`; `patch -p1` in this order: `dxmt-async-pipeline`, `dxmt-render-targets`, `dxmt-command-msl31`, `dxmt-msaa-clamp` (`-v0.80.patch`); AW's variant also `dxmt-mesh-no-ps-v0.80.patch`. `DEVELOPER_DIR=/Applications/Xcode.app/Contents/Developer` (Xcode with the Metal toolchain), `meson setup build64 --cross-file build-win64.txt --buildtype release -Dnative_llvm_path=<any dir with include/ and lib/> -Dwine_install_path=<DXMT CI's wine v8.16-3shain>` (only to configure: the unix side and airconv are not built), `ninja -C build64 src/d3d11/d3d11.dll` (Homebrew mingw-w64, GCC 16.2.0), `x86_64-w64-mingw32-strip`. Verified: same size (3 723 264) and identical code to the payload (disassembly differs only in addresses into `.data`, which is 0x80 bytes smaller because the embedded Metal library was compiled by Metal 32023.864 instead of 32023.922). The native AW copy keeps the DOS stub (no builtin mark). - **DXMT unix side** (`winemetal.so` with airconv): LLVM `llvmorg-15.0.7` built with DXMT CI's flags (`-DCMAKE_OSX_ARCHITECTURES=x86_64 -DLLVM_HOST_TRIPLE=x86_64-apple-darwin -DLLVM_ENABLE_ASSERTIONS=On -DLLVM_ENABLE_ZSTD=Off -DCMAKE_BUILD_TYPE=Release -DLLVM_TARGETS_TO_BUILD="" -DLLVM_BUILD_TOOLS=Off`, plus `-DCMAKE_POLICY_VERSION_MINIMUM=3.5` for CMake 4), then `meson setup … -Dnative_llvm_path=<llvm install> -Dwine_install_path=<wine v8.16-3shain>`, `ninja src/winemetal/unix/winemetal.so`, `strip -x`. Check: an unchanged v0.80 build has the same linkage, minos and all 40 DXMT/Wine interface exports as the release's winemetal.so (only LLVM/libc++ internals differ). The engine's copy is re-signed by install-engine, so compare the PE `winemetal.dll` to pair builds. `launch.sh` runs Advanced Warfare from a clone of the engine's `lib/wine` with its own translator (`kit/payload/steam/aw-winemetal.so` = v0.80 + `dxmt-airconv-ts-workloads-v0.80.patch`; `AW_DXMT_DIR=<dir>` for a whole build under test; `SIL_DXMT_SO=<winemetal.so> SIL_DXMT_CACHE=<absolute dir>` for any Steam D3D11 game). A translator change needs its own `DXMT_SHADER_CACHE_PATH` (DXMT keys translations by shader and variant only). GPU faults with no address: create command buffers with `MTLCommandBufferErrorOptionEncoderExecutionStatus` and label encoders / insert debug signposts in `winemetal_unix.c`; the error's `MTLCommandBufferEncoderInfoErrorKey` then lists each encoder's state (how the AW tessellation overflow was found).
- **Black Ops III Mod Tools' Direct3D 11** (`payload/bo3-modtools/d3d11.dll`, Radiant only): the DXMT x64 PE build above (same tag, same four patches in the same order) plus `dxmt-discard-flush-v0.80.patch` last; same `meson setup` / `ninja -C build64 src/d3d11/d3d11.dll` / strip (3 723 264 bytes). The patch adds `d3d11.discardRenamesPerFlush` (0 = off) and turns it on (1024) by DXMT's own app profile for `Radiant_modtools.exe` only. Check after a change: Radiant's Light step (`-ledSilent … P:/map_source/mp/<map>.map`) under a memory watchdog keeps a flat footprint; with the engine's DXMT it grows by 250-400 MB/s once "Probes...." starts. Diagnosis counters used to find it (Map types, renames, commits, draws, caller stack): private notes. The other Mod Tools files: `msvcr110.dll` from `tools/msvcr110-forward.c` + `.def` (also serializes the Concurrency Runtime's `FlushProcessWriteBuffers`), `embree64r.dll` from `tools/embree-forward.c` + `.def` (forwards to Steam's Embree, copied beside it as `embree64r_steam.dll`; working `SetThreadIdealProcessorEx`), both `x86_64-w64-mingw32-gcc -shared -O2 -s -nostdlib -Wl,--entry,DllMain -o <dll> <c> <def> -lkernel32`; `windowscodecs.dll` = Wine's with `patches/wine-windowscodecs-64bpprgba.patch`. `msvcr110-x86.dll` (the asset database's 32-bit tray, installed by the kit as Steam's prefix `syswow64\msvcr110.dll`) = the same `msvcr110-forward.c` built 32-bit: `i686-w64-mingw32-gcc -shared -O2 -s -nostdlib -Wl,--entry,_DllMain@12 -o msvcr110-x86.dll msvcr110-forward.c msvcr110-forward-x86.def -lkernel32` (the x86 `.def` = every export of Microsoft's 32-bit msvcr110, same ordinals). Check after a change to either: Radiant's Light step headless finishes ("All Probes Done", "Export Done") several runs in a row and Radiant then exits by itself with exit code 0; no "GdtDBTray.0.tmp has encountered a serious problem" window, and `bin\GdtDbTray.log` ends with "… gdtDb.exe /verbose /update] (…) - Process terminated" without "ReadDirectoryChangesW failed" lines.
- Advanced Warfare on DXVK instead of DXMT (development only): `AW_D3D=dxvk AW_DXVK_DIR=<folder with a 64-bit DXVK d3d11.dll and dxgi.dll>` makes them native for AW's exe from `prefix-steam/drive_c/windows/system32` (Gcenx DXVK-macOS 1.10.3-20230507 creates a feature level 11_0 device; MoltenVK then fails on AW's tessellation control shaders). A normal AW start removes the dxgi override again. `<GAME>_TESS_FACTOR=4..64` passes `d3d11.maxTessFactor` to DXMT builds that read it (upstream ef11653; none shipped).
- GPU profile without the screen or root: `xcrun xctrace record --instrument 'Metal Application' --instrument 'GPU' --instrument 'Metal GPU Counters' --attach <pid> --time-limit 4s` (Xcode's developer dir), then `xctrace export --xpath '/trace-toc/run[@number="1"]/data/table[@schema="metal-shader-profiler-intervals"]'`: GPU time per shader under DXMT's function names, limiter counters every 10 µs (`gpu-counter-value`), and `displayed-surfaces-interval` (direct-to-display or not, and why). The Metal HUD log can share lines with other output: keep only lines that start with a timestamp.
- `SIL_DXMT_SO=<winemetal.so> SIL_DXMT_CACHE=<absolute folder>` (development only): a Steam Library Direct3D 11 game runs from a clone of the engine with that DXMT translator and that translated-shader database.
- Metal debugging that worked: `MTL_SHADER_VALIDATION=1` (default fail mode zerofill: the game keeps running and every invalid access is logged; `MTL_SHADER_VALIDATION_THREADGROUP_MEMORY=0` keeps mesh shaders running), translated shaders from DXMT's cache (`shaders_*.db`, table `cache_18`: metallib → AIR bitcode → Homebrew `llvm-dis`), GPU faults in the kernel log via `/usr/bin/log` (zsh's `log` builtin hides it).
- **Wine modules** (winemac.so, winecoreaudio.so): CrossOver 26.3 sources configured as `install-engine`'s engine; winemac patches apply in this order: mouselook → transparent-cursor → game-presentation → mouselook-position. `MACOSX_DEPLOYMENT_TARGET=14.0 make dlls/<x>/<x>.so`, `strip -S`, `codesign -fs -`, add the previous payload sha to the accepted list in launch.sh. Build deps (Homebrew): bison flex freetype sdl2 gnutls vulkan-headers mingw-w64 meson ninja.
- **Battle.net's Wine modules** (`payload/battlenet/ntdll.so`, `win32u.so`; used only by Battle.net's engine clone): in an APFS clone of the configured CrossOver 26.3 tree, apply `patches/wine-ntdll*.patch`, then `patches/battlenet/wine-ntdll-rosetta-privileged.patch`, `wine-ntdll-game-bundle.patch` (made on top of the previous ones: its context includes the x87 sidecar call) and `wine-win32u-memory-size.patch`; `MACOSX_DEPLOYMENT_TARGET=14.0 make dlls/ntdll/ntdll.so dlls/win32u/win32u.so` (without it the modules require macOS 15.5), `strip -S`; Siliconium signs them when it makes the clone. With the Xcode command line tools of macOS 15+, Wine's configure reads library names from `otool -L` output it no longer parses: in `include/config.h` set `SONAME_LIBFREETYPE "@rpath/libfreetype.6.dylib"` and `SONAME_LIBVULKAN "@rpath/libvulkan.1.dylib"`, and build with `make … "LDFLAGS=<the Makefile's LDFLAGS> -Wl,-rpath,@loader_path/../../../lib64"` (a Makefile edit is lost: make regenerates it). Check: `strings -a win32u.so | grep @rpath/lib` shows both names and `otool -l` lists the `../../../lib64` rpath, as in the engine's own modules (without them Battle.net finds no fonts and quits, and console programs crash dividing by zero). Note: the engine's own `ntdll.so` is an older binary that a rebuild from `patches/wine-ntdll.patch` does not match exactly (thread QoS opt-in vs opt-out; a 32-bit breakpoint re-arm path that the patch's condition leaves dead); Battle.net's module is built from the patch text as it is. Check the game bundle without a game: in Battle.net's prefix, `SIL_GAME_EXES=x.exe` and a program started by another (`wine cmd /c start "" x.exe`): its executable is `<Wine's temp folder>/winetemp-…/x.exe.app/Contents/MacOS/x.exe` (`lsof -p <pid> -Fn`), its command name stays `x.exe`, and other programs still run from Wine's links.
- Battle.net development switches (settings.conf): `BNET_ENGINE=<engine folder>` (Battle.net and its games on an engine under test), `BNET_WINEDEBUG=<channels>` (a Wine trace of Battle.net and its game in `logs/battlenet.log`), `GAME_MODE=0` (no app bundle, as for every game).
- **GLDirect** (`payload/steam/cod1-gl/opengl32.dll`, Call of Duty on Steam): github MrRendroc/gldirect commit `69ed709` + `git apply patches/gldirect-cod1.patch`. Homebrew mingw-w64 (GCC 16.2), `i686-w64-mingw32-gcc -O2 -msse2 -mfpmath=sse -march=pentium4 -fno-strict-aliasing -fcommon -w -std=gnu89 -fms-extensions -include src/mingw_compat.h`, defines `WIN32 NDEBUG _WINDOWS _USRDLL _WIN32 MESA_MINWARN __WIN32__ NO_LICENSE BUILD_GL32`, include dirs `src mesa/include mesa/src/mesa/{main,glapi,,x86,math}`; sources = the Release|Win32 file list of `gld9.vcxproj` + `MesaLib.vcxproj`, plus `src/gld_prof.c`. Link: `-shared … opengl32.def -static-libgcc -Wl,--enable-stdcall-fixup -Wl,--kill-at -Wl,--image-base=0x6aac0000 -ld3d9 -ld3dx9_43 -ldxguid -lwinmm -lgdi32 -luser32 -ladvapi32` (mingw's automatic image base depends on the output path). Check: with that image base, `.text` and `.data` are identical to the payload; only the PE timestamp, checksum and the `__TIME__` string differ.
- **Release builds of the unix half** (`aw-winemetal.so`): build LLVM and DXMT under a neutral folder (for example a disk image mounted at `/Volumes/dxmt-build`), as DXMT's CI does under `/Users/runner/work`. LLVM's assertion messages and the Metal compiler keep absolute source paths (the Metal compiler ignores `-ffile-prefix-map`), so a build in a home or temporary folder carries that folder's path. Check before shipping: `strings -a <file> | grep -E '/Users/|/private/'` lists only neutral paths.
- **Helpers**: `tools/iw6-restore.c`, `tools/dialog-guard.c`, `tools/pad-mapper.c` with `zig cc -target x86_64-windows-gnu` / `x86-windows-gnu`; `tools/iw6-focus.swift` with `swiftc -target arm64-apple-macos14.0` + `codesign`.
- **x87-bundle** (`payload/x87/x87-bundle`, in front of x87sidecar for the Game Mode bundle): `clang -O2 -arch arm64 -mmacosx-version-min=14.0 -o kit/payload/x87/x87-bundle kit/tools/x87-bundle.c`, then `codesign -s - kit/payload/x87/x87-bundle`. Check after a change: a Plutonium game with `X87_LOGS=1` logs "starting … under …/x87-bundle" and "x87: acceleration on", and `ps -o command= -p <game pid>` shows the "Siliconium Game.app" loader.
- **Restore helper resident mode**: `iw6-restore.exe --wait [program]` restores the game's window once per line read on its standard input and answers `1` (restored) or `0`, and exits at end of input (iw6-focus keeps one running from the game's start). Check: back from Cmd-Tab the game's log shows "restored the game window in Wine" and the picture is back within about a second.
