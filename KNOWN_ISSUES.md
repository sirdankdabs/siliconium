# Known issues

Each entry: symptom, what is proven, what is not. Evidence details: the private notes
(`Siliconium-Notes/EVIDENCE-LOG.md`, outside the repository).

### Ghosts (Steam and Siliconium's own)
- Ambient Occlusion (any) and Tessellation (Near) each make the GPU page-fault after 45 s - 3.5 min (`kIOGPUCommandBufferCallbackErrorPageFault`, then every command buffer ignored: frozen game); both together also crashed Apple's shader compiler (MTLCompilerService). ### Black Ops III (Steam)
- Performance at Extra detail, 2560x1440, M1 Pro (Zombies, snow map): about 55 FPS, GPU-bound (≈17 ms of GPU work per frame; Metal System Trace with the shader timeline). Largest costs: an always-on full-screen pass (depth-of-field-like, ~25 %), order-independent transparency resolve (~23 %; OIT off: 61-64 FPS), tiled deferred lighting. Limiter counters show those passes latency-bound, not saturated. Tried without gain: OITLayers 16 → 8; one counter atomic per SIMD-group in DXMT's translator (no gain on M1 Pro in a microbenchmark). The two busiest game threads use ~8.5 ms per frame under Rosetta: about 110-120 FPS at most even with a faster GPU.
- Frames are composited by the window server (Metal HUD "Composited"; direct-to-display "display rejected"): costs latency, not measurable throughput. Cause not investigated.
- In play, 3-8 frames every second take 31-44 ms while the GPU time stays normal (~11-14 ms): felt as small regular hitches (Shadows of Evil, 1920x1080, M1 Pro, macOS 27; also seen by the player). Not caused by Game Mode. Cause not known yet.
- On the first visit to a map, a freeze of 0.2-0.7 s when play starts (BOIII on Ascension: 669 + 375 + 225 ms; Black Ops II on its maps: 206-656 ms). Cause not known (no frame of it is GPU work).
- One crash on the very first start (null read in the game's code, ~45 s in, while it downloaded its first-run content); not repeated in later starts.
- Something in the game's process tree runs `curl` (progress meters in the game log); not identified.

### Black Ops III Mod Tools (Steam)
- **Fixed: lighting from the launcher (Light) bakes, exports and Radiant closes by itself** (Windows exit code 0; 6 of 6 headless runs on a one-room map: export in about 4 s, Radiant done in 15-23 s; a Zombies test map from the ZM template: 65 s the first time, then linked: 24 MB fastfile). The launcher's whole Build (Compile + Light + Link) clicked through and Light from Radiant's own window are not re-tested since these fixes.
- **Map sounds: the link reports "sound aliases failed to load"** (exit code 80; the fastfile is still written). Cause proven: the linker runs `sound/snd_convert.exe`, a .NET program, under Wine Mono; Mono runs the static constructor of its `SoundData` class (marked beforefieldinit) when it compiles `Main`, before `Main` stores the source folder from its arguments, so the constructor fails on a null path and no sound zone (`<map>.all.alias.sz`) is made. Microsoft's .NET runs it at the first use, after that. With Wine Mono's interpreter (`WINE_MONO_AOT=interp`) the sound zones are written, but converting a sound then crashes inside Mono (the converter is a mixed C++/CLI assembly). Not fixed.
- **Live updates of edited assets do not reach the editors**: the asset database watches its folders for changed GDT files, but Wine on macOS has no folder-change notification (its server implements it with Linux's inotify only), so a watch never reports anything. Edited assets are picked up when the launcher next starts (it runs `gdtDb /update`). The watch no longer spins (fixed: Wine refused its change kinds, see the changelog).
- **Running a map from the launcher (Run) does not reach the game yet**: Black Ops III starts from the workspace with `+set fs_game <map> +devmap <map>`, fullscreen at the display's mode, then uses about 3.3 cores with the GPU idle and draws nothing for 8 minutes (one-room test map with preview lighting and missing sound zones). Cause not investigated; the Steam Library's own Black Ops III start is a different path.
- Fixed: GdtDBTray (the asset database's tray program, 32-bit) crashed at each start ("Program Error" dialog, page fault reading 0x3E4).
- The linker still gets the performance cores only (8 on an M1 Pro): it hung once with all 10 cores; 11 later links with all 10 cores finished, without a measurable speed difference, so the limit stays until the cause of that hang is known.
- Radiant reports "Failed hardware test for feature: AVX" (Rosetta does not advertise AVX); `ROSETTA_ADVERTISE_AVX=1` not tested.

### Advanced Warfare (Steam)
- **Fixed (2026-11-20): froze 10 s - 1.5 min into gameplay** (GPU page fault, `kIOGPUCommandBufferCallbackErrorPageFault`, then every command buffer ignored), in every run, also with upstream DXMT (main, 2026-11-10). Cause: DXMT's emulated tessellation (D3D11 hull/domain → Metal object/mesh shaders) declares at most 8 mesh workloads per quad patch at tessellation factor 8, but its generator emits 9 when the two inner factors differ with one odd (8 and 7, 8 and 5); the extra workload is written past the object payload and the object stage dispatches more mesh threadgroups than the pipeline declared. Metal shader validation does not instrument the payload or the mesh grid, so it never showed. Every AW hull shader is quad/integer. Found with per-encoder error status: only the encoders with tessellated draws were affected. Fixed together with two related DXMT bugs in the same code (the two patches of an object threadgroup raced on a shared workload counter; the mesh-threadgroup limit was declared for one patch while two patches' workloads are dispatched): `patches/dxmt-airconv-ts-workloads-v0.80.patch` → `payload/steam/aw-winemetal.so`, used by AW only from a clone of the engine (its own translated-shader cache `airconv-aw5`). First mission: 15 min of play without a fault (M1 Pro, macOS 15.8.3, 2560x1440 at 160 Hz, Extra textures), 108 FPS average, GPU median 8.7 ms. A long session with the shipped build is still to be done.
- Ruled out on the way (each tested): ambient occlusion, the tessellation factor, the translator's bounds handling, the dispatch-argument kernel, index-format pipeline reuse, out-of-range index/vertex reads (checked on the CPU for every draw), DXMT packing two patches per object threadgroup.
- On DXVK (MoltenVK) instead: the mission never finishes loading: MoltenVK cannot compile AW's tessellation control shaders (`redefinition of 'gl_PrimitiveID'` in the generated Metal source).
- Mission loads: ~100 s loading screen after the intro cinematic even with warm caches (the game's shader preload; one game thread CPU-bound under Rosetta, the other threads idle); a cold shader cache adds minutes. To try: preloading during the cinematic, or no preload (warm DXMT/Metal caches).
- Closed when the first mission's cutscene ended: `Mesh Render Pipeline Descriptor Validation: fragmentFunction must not be nil` (Metal assertion). DXMT 0.80 builds a tessellation pipeline with colour attachments and no pixel shader; upstream fixed it in commit ab984cf (after 0.80, not released). **Fixed (owner saw the cutscene end)**: an AW-only `d3d11.dll` (DXMT 0.80 + our 4 patches + `dxmt-mesh-no-ps-v0.80.patch` = ab984cf unchanged), `payload/steam/aw-d3d11.dll`, native for `s1_sp64_ship.exe`/`s1_mp64_ship.exe` only (`AW_DXMT_FIX=0`: the engine's DXMT). Every other game keeps the engine's DXMT.
- Exo Zombies / Multiplayer chosen from the campaign's menu now start through Siliconium (own setup, fullscreen at the display's mode), but stay at "Connecting to online services" (not investigated: Activision's online services for AW on PC, or Wine networking). After that switch the campaign crashed on its way out once (page fault in the game's code, Wine's "Program Error" box). Steam's launch-option dialog can open behind other apps (bringing it forward is built, not tested).

### Infinite Warfare (Steam)
- Without Advanced Warfare's two DXMT fixes it does not play: DXMT 0.80 aborts it during the first shader preload (`Mesh Render Pipeline Descriptor Validation: fragmentFunction must not be nil`, fixed upstream in ab984cf), and with only that fix its GPU page-faulted ~1.5 min into the first mission (`kIOGPUCommandBufferCallbackErrorPageFault`). Its tessellation (on by default, "Near") uses the same emulated tessellation path as AW: 155 triangle and 18 quad hull shaders in the first missions. Siliconium runs it with both fixes; `IW7_DXMT_FIX=0` in settings.conf turns them off.
- DXMT caps tessellation at factor 8 (the game asks for 15), as for AW: tessellated surfaces get less subdivision than on Windows.
- GPU-bound at the game's own settings on an M1 Pro at 2560x1440: ~50-58 FPS in most areas, ~37-40 in heavy fights; the CPU is not the limit (busiest thread ~40 % of a core). Measured per option in one scene: volumetric lighting off −1.7 ms, cached spot shadows −1.4 ms, cached sun shadows −0.8 ms, tessellation off −0.8 ms, motion blur off −0.6 ms; AO, particle lighting and shadow casters ≤0.2 ms each; "Sync every frame" changes nothing under DXMT.
- Memory: the game uses about 10 GB (about 6 GB of it graphics) at its own settings; on a 16 GB Mac much of the rest goes to swap. Not tested on 8 GB Macs. With browsers and other apps open on a 16 GB Mac, macOS compresses and swaps memory while it plays and the game stops for a moment now and then (measured: hitches of 80-175 ms while the GPU waited for the game, during bursts of memory compression; no rendering error). Closing other apps while playing helps; this applies to IW7-Mod too.
- Cache Spot Shadows and Cache Sun Shadows (off in the game's own detection on an M1 Pro): about −2 ms of GPU time per frame, no crash or GPU fault in a 25-minute campaign test, about +0.15 GB of graphics memory. Siliconium leaves them to the player (crashes with shadow caching are reported for this game on other platforms; a longer test is pending).
- Power on an M1 Pro (game's settings, 2560x1440): about 26-31 W in total (GPU 13-16 W at 98-100 % busy), so the fans run. Being GPU-bound, cheaper settings raise the frame rate rather than lower the power. Only a frame-rate cap below what the GPU reaches lowers it (`MAXFPS`, not tested in play yet).
- Frame pacing: when the GPU cannot keep up with the display's refresh rate, frames stay on screen for 1 to 4 refreshes (on a 160 Hz display: 6.25 to 25 ms), so motion is less even than the average frame rate suggests.
- On a scaled desktop (held in a 1x mode while the game runs), leaving the game (Cmd-Tab) switches the display from the game's 1x mode back to the desktop's and back again: an external monitor goes black for a moment both ways. On an unscaled HiDPI desktop the mode is kept (no switch; not tested with this game).
- Changing Render Resolution in its options stops drawing for about a minute while the game rebuilds its buffers (it comes back).
- Its settings file (`players2/config_mp.cfg`) stores settings by hash (`setcl <number> "value"`), not by name; Siliconium writes only the resolution and the refresh rate.
- It asks "You have a Gamepad attached…" at every start while a controller is connected and the keyboard scheme is chosen.

### WWII (Steam)
- In play, a frame of 50-60 ms every 1-3 s (Nazi Zombies, campaign; 1920x1080, M1 Pro, macOS 27) while the GPU time stays normal: CPU-side, not caused by the Metal HUD. Likely the game waiting on Steam, which macOS Game Mode slows down while the game is in front (measured earlier: Steam's answers p90 25 ms with Game Mode, 0.5 ms without). Not fixed yet.
- Loading a campaign mission takes about 2 minutes on an M1 Pro (112 s from Resume to play in the first mission, warm or empty caches; 155-158 s before the shader preload was turned off). Most of it is the game's own pacing, not the Mac's speed: the mission's intro film plays in full (110 s for the first mission; not skippable while loading) and the level data loads in about 10 s at 400-900 MB/s. The game's shader preload (`r_preloadShaders`, a fixed ~40 s at 20 FPS) is off by default because under DXMT it saved nothing in play (`WW2_PRELOAD=1` turns it back on).
- GPU-bound at the game's own settings at 2560x1440 on an M1 Pro: 74-78 FPS in the first mission with macOS Game Mode on (53-54 FPS without it). Nazi Zombies (local solo match, The Final Reich, spawn view): 52-63 FPS with the GPU at 17-22 ms per frame, so GPU-bound there too; Game Mode gives better 1 % lows (18-29 vs 12 FPS). Online Zombies earlier ran at 30-46 FPS with hitches of 0.2-0.7 s while the Mac was short of memory (the game uses about 10-12 GB); on a 16 GB Mac, closing other apps while playing helps.
- Multiplayer on an M1 Pro, 2560x1440 (Team Deathmatch, Pointe du Hoc, standing at the spawn): 62-66 FPS online (custom match) and offline (LOCAL PLAY), held by the GPU (about 14-19 ms of GPU time per frame) and by DXMT's command-encoding thread (close to one full core). The online 33-39 FPS measured before came from the game's per-frame network-state check (fixed by Siliconium's `wininet.dll`, see the changelog).
- The multiplayer start menu runs at about 48 FPS with the GPU nearly idle: its loop waits for the frame cap and makes Steam calls on every turn, and it presents about one frame for every two turns. Matches are not affected. While a game runs in macOS Game Mode, Steam's own process is lowered to background priority and each Steam call the game makes takes longer (median 2 ms, sometimes 25-120 ms, against 0.2-0.4 ms without Game Mode); in a match that cost is small next to the GPU's.
- The game runs a thread of its own at the lowest priority that keeps listing every window and reading its title (about one core while loading and playing). It is left at that priority on purpose: raising it measured no gain and worse 1 % lows.
- The first LOCAL PLAY match asks macOS for local-network access for "Siliconium Game" (local and LAN matches need it; online play does not).
- The first time the multiplayer executable starts it picks 1280x720 by itself; Siliconium passes the display's size on the command line, so it plays at that size anyway (its resolution is not read from `players2/user_config_mp.cfg`; it lives in the encrypted `system_config_mp.cfg`). Its frame cap is the other way round: read from `user_config_mp.cfg` (`com_maxfps`, set to the display's rate at each start), ignored on the command line. A frame-rate limit chosen in the game's own settings is replaced by the display's rate at the next start.
- The campaign's Multiplayer / Nazi Zombies buttons: Steam asks for a launch option and then to confirm "+zombiesMode 1" in its main window, which stays minimized under Wine. Siliconium's relay starts that part itself instead (not yet verified from a rebuilt app); the app's own Multiplayer and Nazi Zombies buttons do not go through Steam's questions.
- The game uses tessellation: DXMT caps the factor at 8 (the game asks for 64), as for Advanced Warfare and Infinite Warfare. No GPU fault seen in ~25 minutes of campaign and a Zombies match.

### Infinite Warfare (IW7-Mod (CBServers))
- Validation in progress (see COMPATIBILITY.md); neither CBServers nor AuroraMod mention macOS.
- A custom map that ships no English text file (`usermaps/<map>/eng_<map>.ff`) shows raw labels (e.g. `CP_PROTOTYPE_INTRO_LINE_1`) instead of its text; that file comes from the map's author.
- The first start downloads IW7-Mod's data (about 400 MB from CBServers' update repository on GitHub, with AuroraMod's server as a fallback) before the game opens; Siliconium waits up to 20 minutes for it. Its updater also replaces iw7-mod.exe with newer builds by itself.
- It asks your router to open its game port (UPnP, `nat_upnp`, on by default; set it to 0 in its console to stop). Whether this works under Wine is not verified.
- A Steam download is played from IW7-Mod's own copy in Siliconium's folder (`iw7mod/`), made of APFS clones at each start (no extra space, under a second). A minute after the game quits the game's files leave it again, so between games it holds only IW7-Mod's own files (a few MB); while you play, Finder shows it at the game's full size (about 100 GB) although it uses no extra space. It needs Siliconium's folder and Steam's library on the same APFS volume (always the case for the Steam Library); otherwise Siliconium refuses instead of copying the whole game.
- IW7-Mod keeps its own profile and campaign saves in its copy's `iw7-mod/players2` (the Steam game's stay in Steam's `players2`); the first time it starts from a copy of the game's settings file. "Remove setup" keeps them.
- Custom maps go where IW7-Mod looks for them: the game folder's `usermaps/<map>/<map>.ff`. For a Steam download you can put them in Steam's game folder: they reach IW7-Mod's copy at its next start (no extra space), and a map deleted there is gone from the copy at the next start too.
- Its data lives in Steam's Wine prefix (`AppData\Local\auroramod\iw7-mod`, shared with AuroraMod's client) and its identity keys in `AppData\Local\cbservers`.

- Some servers refuse players without Steam: "Steam is not installed. In order to play on CoD4X18 servers you have to install and run Steam…" or "Steam is not running…". The text comes from the server's own authentication module (CoD4X's `steam_api.so`, closed source) when its admin sets `sv_steamforce` (default off). Since this release Play CoD4X starts Steam for Windows in the background when it is set up in the Steam section and signs in by itself (`COD4X_STEAM`, on by default). Not verified yet: joining such a server with it. Not tested either, though very likely: the server only accepts a Steam ticket that Steam validates as OK, so the account most likely has to own Call of Duty 4; a disc copy without it on Steam plays only on the other servers. Disc CD keys of Call of Duty 4 generally cannot be activated on Steam (players' reports, not official).
- A Steam download is played from CoD4X's own copy in Siliconium's folder (`cod4x/`), made of APFS clones at each start (no extra space); a minute after the game quits the game's files leave it, so between games it holds only CoD4X's files (a few MB). If Steam's library is on another disk (no clones possible), the copy is a real one (about 7 GB), kept between games and brought up to date at each start; it is emptied when the game is no longer in Steam.

## Solved in 1.1.0 (cause → fix)
- BOIII (Ezz) v3.1.0 closed as the lobby loaded (`EXCEPTION_ACCESS_VIOLATION`, its server thread, reading the name's letters as an address) → Siliconium 1.0.0 padded short player names with `^7` to 16 bytes (Ezz v3.0.0 crashed with shorter names); with v3.1.0 the padded default name crashed and an unpadded 11-character name played → the padding is no longer added and 1.0.0's is removed; the default name is "Siliconium". Not re-tested in game with a name shorter than 11 characters (the default "Siliconium" has 10).
- Call of Duty (Steam) at 44 FPS → Apple's OpenGL waited for the GPU inside `glBufferSubData` (41 % of the render thread, `sample`) → the game draws through our GLDirect build (OpenGL → Direct3D 9 → DXVK): 137-159 FPS at 2560x1440. Rejected on the way: QindieGL (crashed CoD1 at start: fake `wglCreateContextAttribsARB` pointer).
